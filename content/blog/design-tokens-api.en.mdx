## Variables ≠ system

`--blue: #0070F3` is not a design token. It's a string in CSS. It becomes a token when it has a name describing a role (`accent`, not `blue`), stability (the value may change, the name may not), and a contract (every consumer uses it the same way).

Same difference as between "we have a function" and "we have an API". An API is a promise.

## Three layers that work

In mature systems, tokens live in layers, each solving its own problem:

1. **Primitives** — raw material: palette, type scale steps, spacing scale. `gray-900: #171717`. Nobody uses these directly in components.
2. **Semantics** — roles: `surface-0`, `text-primary`, `accent`. This is where dark/light themes live: layer 2 gets remapped, components stay untouched.
3. **Component layer** — `button-primary-bg`, `card-border`. Debatable: needed when the same role must differ across components. Two layers are often enough.

## What it buys in practice

In this portfolio, the light theme is a single block of semantic-layer overrides. Zero component changes. Theme switching is rebinding values, not rewriting consumers. That's the payoff of a contract: dozens of components depend on 13 names, not on 13 values × 2 themes × N usage sites.

## Where it breaks

Classic cracks: a "temporary" hex in a component that stays forever; a 17px margin because "it looks nicer here"; a third accent color because "the client asked". Each crack is small, but systems don't die from one blow — they die from a thousand exceptions.

My rule: if a value doesn't fit the scale — question the scale first, not the value. Sometimes the scale is incomplete and worth extending. More often, the solution just isn't thought through.

## Bottom line

Design tokens are the interface between design and code, with all the attributes of an API: naming, versioning, backward compatibility, and cost of change. Treat them like an API — they'll pay you back in predictability. Treat them like variables — and you'll get CSS that's afraid of refactoring.
